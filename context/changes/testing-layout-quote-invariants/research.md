# Research — test-plan Phase 4: layout and quote invariants (risks #4, #5)

## Question

What do the existing tests already prove for risk #4 (an impossible or rule-breaking layout, from a
proposal or a manual edit) and risk #5 (a wrong quote), are the quote tests' expectations independent
of the code, and which gaps are worth a test? Source of the ask: `change.md`, test-plan §2 Risk
Response Guidance rows #4/#5, §6.5, §6.6 Phase 4.

## Answer in short

- **#5 — the arithmetic is covered with independent literals; the device count is not.**
  `src/lib/quote.test.ts` states (`:19-23`) and keeps the rule that every expected number is
  worked out by hand: each expectation is a literal (`51_213`, `87_212`, `27_113`…) with the hand
  computation in a comment, never re-derived through `estimateLabourMinutes`/`labourCostGrosze`. So
  the formula, the half-up rounding boundary (`labourCostGrosze` table `:66-76`, including the exact
  .5 case and the int4 maximum), the profile-first block (`:179-182`), `not_current` for the four
  other match states (`:184-186`), the override and its `outdated` flag (`:188-207`) and the busbar
  piece rule (`:150-171`) are already proven from hand-computed examples.
  **The gap is "the device count is the list length"** (the §2 "must challenge" for #5): every
  `computeQuoteView` test hands in snapshot rows the test wrote itself, so the tests _assume_ that the
  snapshot holds exactly the mounted devices. `computeQuoteView` sets `deviceCount =
matchView.snapshot.length` (`src/lib/quote.ts:147`). Nothing ties a real project — circuits, a
  catalog, a cabinet — through `matchDevices` to the count and the material cost that an electrician
  would get by counting the bill of materials by hand. The rows come from the matcher
  (`selections.push` in `src/lib/device-matching.ts` for the main switch, MCBs, RCBO, RCD, bars;
  busbar segments appended last, `:523`) and the snapshot trigger copies one catalog row per
  selection; the kitchen-sink fixtures do build a quote through the matcher
  (`src/lib/kitchen-sink-circuits.ts:794-830`) but only to render states, with no expectation.
- **#5 — no property-level check of the rounding.** The rounding is proven on six table rows; there
  is no independent oracle over arbitrary minutes × rate, nor metamorphic checks of the formula
  (one more device = exactly one more mount time; one more segment of an already-bought busbar piece
  = more labour, no more material; row order does not matter).
- **#4 — largely delivered; one real gap.** A fast-check proposal test exists:
  `src/lib/cabinet-layout.property.test.ts:190-216`, 400 runs per geometry, asserting placement
  coverage, determinism, two-decimal offsets and `validateLayout(...) === []`, with a distribution
  guard (`placed > 20`). Its generator (`:83-108`) covers FR 1–4P, up to 5 RCD groups, single-circuit
  groups as RCBO _or_ the RCD+MCB fallback, comb busbar rows, catalog PE/N bars and 1P…4P shapes.
  Geometries (`:70-76`): the three seed fixtures (`cabinet-layout.fixtures.ts`) and a hand-built
  `PITCHED` one. Manual edits: `src/lib/layout-editing.property.test.ts:121-160`, 300 runs on the three
  seed geometries, accepted moves keep `validateLayout` empty, refused moves change nothing. E2E:
  `tests/e2e/layout-manual-edit.spec.ts`.
  **The gap:** the production cabinets — the 33 Karwasz models in `src/lib/karwasz-cabinets.ts`
  (`KARWASZ_CABINETS` `:82`, geometry built by `karwaszGeometry` `:182`) — are never run through
  `proposeLayout` or the edit model. `karwasz-cabinets.test.ts` pins only the generated SQL and the
  parser. Their geometry is synthesised by rules not used by the seed fixtures: centred rails 125 mm
  apart, two entries, and built-in N/PE bars placed side by side, stacked, or overlapping at z 20/35
  (`karwasz-cabinets.ts:13-21`, `:140-176`); the UNI SYSTEM models have no bars at all, so catalog
  bars are required. These are the geometries electricians actually pick in production.
- **#4 — single-circuit group → RCBO is a matcher rule, not a layout rule, and is tested there.**
  `validateLayout` (`src/lib/cabinet-layout.ts:938-1017`, codes `:881-891`) forbids an RCBO sharing
  its group (`rcbo_not_alone`) but does not require a single-circuit group to be an RCBO — it must
  not, because the matcher's RCD+MCB fallback (`device-matching.ts:410-423`, note `rcbo_fallback`) is
  a valid result when the catalog has no compliant RCBO. The rule is proven in
  `device-matching.test.ts:498-516` (RCBO chosen) and `:520-` (fallback flagged), and both shapes are
  generated by the layout property test. No gap.
- **Visual review.** The drawing and printout have unit tests of helpers and of the print view
  (`cabinet-drawing.test.ts`, `quote-print.test.ts` — gates, material lines summing to
  `devicesGrosze` and throwing otherwise, letterhead, notices), but nothing deterministic detects an
  unreadable drawing (labels colliding, wires obscuring devices, the table spilling to a second page —
  the last is an open note in `context/archive/2026-10-08-printable-quote-export/reviews/impl-review.md:83`).
  §4 allows a 1–2-screen multimodal review there; `/dev/kitchen-sink` renders the printout states from
  fixtures with no database.

## Where the quote is consumed (no second sum)

`computeQuoteView` callers: `src/pages/dashboard/projects/[id].astro:183`,
`src/pages/dashboard/projects/[id]/print.astro:110` (into `computePrintView`),
`src/pages/api/projects/[id]/quote.ts:73` (server-side override base). `devicesCostGrosze` has one
caller (`quote.ts:148`). `quote-print.ts` `materialLines` regroups the snapshot for the printout and
throws when its lines do not sum to `devicesGrosze` (`:132-134`) — a parallel computation guarded by an
equality, already tested (`quote-print.test.ts:189-209`). The e2e `tests/e2e/quote-override.spec.ts`
already covers the override endpoint (refusals, server-side base) and is out of scope here.

## Gaps considered and rejected

- **A second, hand-written geometric oracle next to `validateLayout`.** §6.5 decides that
  `validateLayout` is the single definition of layout correctness and the test does not write its own;
  the validator's own negative cases are hand-written literals in `cabinet-layout.test.ts`. Keep.
- **The edit property test on `PITCHED` / busbar groups.** The edit generator
  (`layout-editing.property.test.ts:44-56`) already includes RCBO groups and a catalog bar; busbar rows
  are never placed, so a move never touches them. Extending its geometries with the Karwasz set covers
  the stronger gap; `PITCHED` adds little.
- **A new e2e for the quote numbers.** The page renders `computeQuoteView` as is (`[id].astro:183`,
  `QuoteSection.astro:113` only formats); the arithmetic belongs in unit tests (§2 #5 cheapest layer:
  unit). No new spec.
- **A materialLines/devicesCostGrosze mismatch.** `materialLines` keys by `(device_id, price_grosze)`
  while the cost keys busbars by `(device_id, busbar_piece)`; any disagreement throws — the safe
  direction, already tested.

## Recommended scope for the plan

1. Quote worked examples through the real matcher: 3–4 small projects with a hand-written fixture
   catalog, each with a hand-counted bill of materials (count, material grosze, minutes, labour grosze)
   as literals — including an RCBO, the RCD+MCB fallback, catalog PE/N bars on a bar-less cabinet,
   comb busbar segments sharing a piece; plus the no-profile block and an override on a real project.
   The only adapter is selection → row by catalog id (what the snapshot trigger copies).
2. A quote property test: the rounding against its definition (BigInt: `m·r − 30 < 60·c ≤ m·r + 30`),
   and metamorphic relations on rows.
3. The production Karwasz geometries in the proposal property test (and the edit property test), with
   a per-geometry non-vacuity guard tuned to small cabinets.
4. Docs: §3 Phase 4 `complete`, §6.5 Quote pattern, §6.6 Phase 4 note; a dated multimodal review of
   the printout on `/dev/kitchen-sink` as an optional manual step.

## Open facts / limits

- Whether every Karwasz geometry accepts some generated device set is unknown until run: the
  smallest (RN-6-P, 1×6 modules, 105 mm of rail) may fit almost nothing; the guard must be per
  geometry class, not a blanket `> 20`.
- Run time: 33 geometries × 400 runs may be slow; the plan should bound runs and measure.
